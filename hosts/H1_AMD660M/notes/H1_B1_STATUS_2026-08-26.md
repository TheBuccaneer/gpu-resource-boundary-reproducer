Dynamic local-memory boundary:

- 65536 B -> PASS / F0
- 65537 B -> compute scheduler timeout, process abort,
  successful compute-ring reset / F2 + F5

Smallest observed failing delta:
+1 byte

The +1-byte kernel accesses only byte 65536 of the 65537-byte allocation
requested through clSetKernelArg. It does not intentionally access outside
the requested local-memory object.

## Root-cause evidence

Dynamic local memory is:

1. accepted and stored by Rusticl;
2. incorporated into variable_local_size;
3. forwarded as pipe_grid_info.variable_shared_mem;
4. combined with static shared memory by radeonsi;
5. converted to LDS blocks using 512-byte encoding units on GFX10.3;
6. encoded into COMPUTE_PGM_RSRC2.LDS_SIZE.

Boundary arithmetic:

65536 B -> 128 encoded units
65537 B -> align(65537, 512) = 66048 B -> 129 encoded units

The examined dispatch path does not revalidate this total against the
device's 65536-B lds_size_per_workgroup capacity before submission.

Current root-cause wording:

A device-specific per-workgroup LDS capacity invariant is not revalidated
when dynamically sized OpenCL local-memory requirements are incorporated
at dispatch time. On the tested GFX10.3 system, a one-byte excess over the
advertised 64-KiB limit is propagated into radeonsi's compute resource
state and is followed by a compute-ring timeout and ring-level recovery
instead of controlled OpenCL resource failure.

## Static vs dynamic

Static oversized local memory and dynamic oversized local memory expose
the same resource contract at different enforcement stages.

Static:
compile/backend-time resource modelling -> process failure.

Dynamic:
dispatch-time resource incorporation -> missing capacity revalidation ->
GPU compute-ring timeout/reset.

Do not currently claim a proven hardware-level zero-occupancy mechanism.
